# External end-to-end benchmark options

Use this comparison when choosing an end-to-end theorem-solving evaluation for the current JevLean search. It evaluates whether the search can produce a complete, replayable Lean proof. It does not treat next-tactic accuracy or premise-retrieval accuracy as theorem-solving success.

Time-sensitive repository and dataset facts below were checked on 2026-09-18. Commit hashes are included because default branches and hosted datasets can change.

## Evaluation requirements

A useful comparison should:

- build close to JevLean's Lean `v4.30.0` and Mathlib `c5ea00351c28e24afc9f0f84379aa41082b1188f` environment;
- have enough accepted tasks to distinguish search changes without making a first run prohibitively expensive;
- expose formal statements independently of any reference proof;
- let the runner construct the declaration environment that existed before each target;
- support fresh-process replay without `JevLean` imports; and
- have a recognizable published protocol or a fully frozen derivation recipe.

“Proof available” below means a formal Lean proof is distributed. An informal solution does not give the kernel a proof, but it remains a contamination risk for models trained on mathematical text. Adaptation cost assumes the leakage controls in [BENCHMARK4.md](BENCHMARK4.md): prefix-only materialization, target removal, suffix exclusion, sanitized workers, and independent replay.

### Options not selected as end-to-end theorem benchmarks

[QuantumLean-Bench](https://github.com/lean-dojo/QuantumLean-Bench) is current and pins Lean `v4.24.0`, but its 931 quantum-science records mix numerical, algorithmic, informal, formalization, and theorem tasks. The formal protocol asks a model to construct Lean snippets against supplied domain scaffolds. It is not a homogeneous fixed-formal-statement proof-generation benchmark for the current JevLean interface.

The original [FIMO repository](https://github.com/liuchengwucn/FIMO) is Lean 3. The Lean 4 port above is the relevant candidate.

## Next-step and premise-selection data are different evaluations

A next-step dataset contains a proof state and an author tactic. Exact-match or Lean-checked continuation measures local action prediction. It does not require the system to close the theorem, and there may be many good next actions that differ from the recorded one. JevLean's Sipser 100-task study is in this category.

A premise-selection dataset asks a retriever to rank declarations used by a reference tactic or proof. Recall, mean reciprocal rank, or nDCG measures retrieval. It does not establish that search can compose retrieved declarations into a proof. Reference-proof labels can also be incomplete because a different proof may use different premises.

[LeanDojo](https://github.com/lean-dojo/LeanDojo) traces tactic states and premises and supplies random, novel-premises, and novel-proofs splits for training and local evaluation. [LeanDojo Benchmark 4](BENCHMARK4.md) can be used for end-to-end proving only when a prover starts at each theorem and must close it under the frozen environment. Its traced tactics and premise annotations must remain hidden from the runner. [LeanDojo-v2](https://github.com/lean-dojo/LeanDojo-v2) is an actively developed tracing/training framework, not a newly frozen successor benchmark with a standard held-out theorem list. As checked at commit `baed5eae6e87a65a446d9f54af07aab2154e7599` (2026-08-10), it can trace arbitrary repositories, but that capability does not itself define a comparable split.

These datasets remain useful for diagnosing action generation and retrieval. Their metrics should be reported separately from theorem solve rate.

## A native Mathlib 4.30 benchmark

A benchmark derived from a recent pinned Mathlib revision gives exact environment alignment and broad library-style mathematics. It is not initially an external standard, so its value depends on publishing the manifest and derivation tool.

Use this construction:

1. Freeze a final Mathlib commit `C`, initially JevLean's `c5ea00351c28e24afc9f0f84379aa41082b1188f`, its Lean `v4.30.0` toolchain, and a contiguous pre-registered commit interval ending at `C`.
2. Enumerate theorem and lemma declarations first introduced in that interval. Exclude generated declarations, deprecated aliases, declarations with unsafe or noncomputable proof shortcuts that the protocol disallows, statements requiring private implementation details, and statements whose original proof uses `sorry` or nonstandard axioms.
3. Group targets before splitting. At minimum, keep declarations from one source file in one group. Also group exact normalized-statement duplicates and mechanically recognizable theorem families. Assign groups by a published SHA-256 rule to 80% development/training, 10% validation, and 10% test. A temporal holdout can be added later, but a naive theorem-level random split is not defensible because adjacent declarations are often variants.
4. For each target, import exactly the target file's transitive imports, copy only the source prefix before the declaration, retain the target statement, replace its proof, and omit the suffix. Do not import the target module or the `Mathlib` umbrella.
5. Build the retrieval index separately for each target from declarations in its transitive imports plus declarations earlier in its source prefix. Exclude the target, every later declaration, declarations from other benchmark files that are not genuine imports, and all reference-proof text and traced-premise labels.
6. Keep the original proof in a sealed answer artifact used only to confirm that the statement builds and to compute post-run analysis. Hash the target source, prefix, import closure, allowed-premise list, and answer artifact independently.
7. Replay accepted ordinary tactic source in a fresh process against the same prefix environment without `JevLean`. Record any nonstandard axioms used.

This prevents direct target lookup, later-declaration leakage, and cross-task admission leakage. It does not eliminate model contamination: Mathlib is public and likely appears in pretraining. Reduce that risk by selecting newly introduced declarations after the model's documented training cutoff when one is known, reporting cutoff uncertainty, and checking generated proofs for suspicious verbatim overlap with the sealed reference proof. Verbatim checks detect copying but cannot prove the absence of contamination.

The adaptation cost is medium. The existing Benchmark 4 runner already implements the core prefix and replay boundary, but the task enumerator, grouped split, per-target import closure, and allowed-premise manifest need to be generalized and frozen.

## Recommendation

### Immediate pilot: 75 miniF2F test theorems

Run a deterministic 75-theorem pilot from the Google DeepMind Lean 4 `Test` split. Order targets by SHA-256 of the canonical theorem name and take the first 75 after the 4.30 port builds. Freeze both accepted and excluded targets; do not replace failures opportunistically. Use formal statements only, no docstrings or reference solutions, and an allowed-premise index containing Mathlib declarations only.

This is the best immediate option because it is recognizable, close to the current toolchain at Lean 4.27, Apache-licensed, likely to produce a nonzero solve count, and small enough for repeated end-to-end runs. Report it explicitly as a high-contamination pilot rather than a clean estimate of novel reasoning.

### Longer-term standard comparison: full miniF2F test

Port and run all 244 standard miniF2F test theorems under the same frozen 4.30 protocol. Publish solve rate and resource budget alongside the exact upstream commit and port patch. This gives the clearest comparison with existing prover literature; validation can be used for development while test remains untouched.

In parallel, build the pinned Mathlib benchmark above as the primary leakage-controlled regression suite. It will be more representative of JevLean's library retrieval and less dependent on an obsolete toolchain, but it should not be called a standard external comparison until its manifest is published and reused independently. Use ProofNet 4.27 next if a second external domain is needed: it broadens beyond competition mathematics with a smaller migration gap than the other alternatives.
